## 1. 先说最重要的结论

当前这个项目最大的问题，不是单个 CSS 或单个函数，而是**运行环境、基线提交、公开 release、当前本地代码经常不一致**。

接手时一定要同时核对这 4 件事：

1. 当前本地仓库 `HEAD` 在哪一个 commit
2. 当前约定基线是 `AA` 还是 `BB`
3. 当前公开 GitHub release 指向哪个 tag / commit
4. 当前机器实际运行的是哪个 `ChordVox.app`

如果只看源码，不看当前 app 包、Git tag、GitHub release 页面和本地运行进程，很容易得出错误结论。

## 7. 目前已经做过的大块工作

### 7.1 辅助功能权限 / 重复黑框 / 中间悬浮窗

这是本轮最反复的一块。

用户复现场景核心是：

1. 第一次按快捷键开始录音
2. 第二次按快捷键结束录音并自动粘贴
3. 若没给辅助功能权限，会弹系统权限提示
4. 点“取消”
5. 第三次再按快捷键时：
   - 重复出现黑色权限提示方框
   - 屏幕中间主悬浮窗又出来

相关文件：

- `src/helpers/clipboard.js`
- `src/helpers/audioManager.js`
- `src/hooks/useAudioRecording.js`
- `src/helpers/ipcHandlers.js`
- `preload.js`

历史上做过多轮 suppress / dialog 修复，关键相关提交包括：

- `d722905 fix: suppress repeated accessibility prompts after cancel`
- `0ef5252 fix: suppress duplicate accessibility paste guidance`
- `362215c fix: suppress follow-up dictation ui after accessibility cancel`
- `6447a19 fix: preserve accessibility paste detection in localized builds`

当前可确认状态：

- `clipboard.js` 里已经把 accessibility dialog 是否真的弹出，显式作为 `dialogShown` / `handledBySystemDialog` 元数据往后传
- `useAudioRecording.js` 里不再用“是否允许弹窗”去推断“本次是否已由系统 dialog 处理”
- 也就是说，之前 review finding 里那条：
  - “`guidanceAlreadyHandled` 把没弹出的情况也当成已处理”
  这条现在从代码结构看已经不再是旧实现

但真正用户侧的“第三次热键又把中间悬浮窗拉出来”这条，**仍未彻底闭环**。

原因：

- 曾经做过一个本地修复提交 `97a07ba fix: suppress no-op hotkey overlay reopen during processing`
- 但这个提交后来按用户要求回退掉了，没有保留在当前分支

所以当前基线里，这条问题仍然应该视为：

- **未完成**
- 需要重新从 `AA` / `BB` 基线重新分析和复测

### 7.4 Success 完成态 / 荧光粉问题

这是当前最需要继续追的 UI 问题之一。

已经确认过的历史事实：

- 曾经有一版 success 被改坏成整条荧光粉
- 后来参考 `implementation_plan.md` 收回为更克制的冷白蓝 success
- 历史上也存在“源码、打包 CSS、运行中的 app 不是同一份”的情况

当前和这条最相关的提交：

- `0abc413 fix: replace fluorescent magenta with rose-violet in recording state`
  - 保留
- `037a4f4 fix: snap success shell visuals to blue palette`
  - 后来被回退
- `4ea74ca Revert "fix: snap success shell visuals to blue palette"`
  - 当前主线上保留

基于当前源码的只读结论：

- `recording` 的壳体主色仍然是偏粉紫：
  - `src/index.css` `dictation-pill-shell--recording`
  - `--shell-mid-rgb: 210, 82, 200`
- `success` 的壳体主色是冷白蓝：
  - `src/index.css` `dictation-pill-shell--success`
  - `--shell-mid-rgb: 157, 220, 255`
- `App.jsx` 中 success / recording 的切换不是由“录音动效下拉选项”决定的，而是由：
  - `micFeedbackState`
  - `dictationStage`
  - `micState`
  决定

当前最重要的新结论：

**“录音动效”下拉项不是荧光粉问题的直接根因。**

原因如下：

1. `recordingAnimationStyle` 的设置链路是通的：
   - `SettingsPage.tsx` -> `useSettings.ts` -> `preload.js` -> `main.js` -> `App.jsx`
2. 它只传给 `DictationAnimation`
3. 它主要改的是内部波形参数，而不是外层胶囊壳体配色

更具体地说，当前所谓 3 种样式其实不是 3 套独立动画系统：

- `line`
  - 17 根柱
  - bar width 5
  - cluster width 196
- `particles`
  - 15 根柱
  - bar width 5
  - cluster width 188
- `level`
  - 13 根柱
  - bar width 6
  - cluster width 178

CSS 层面它们的差异也有限，主要是：

- bar 数量
- 宽度
- cluster 宽度
- `gap`

非常关键的一点：

- 当前 `particles` 并不是真正的“录音粒子云”
- 真正的 `sparkles` 粒子只在 success 时出现，且是 `sparkleCount = 9`

因此，如果用户看到的是：

- **整块胶囊背景都呈现荧光粉**

那么更像是：

- 外层 `shell` 还停留在 `recording` tone
- 或 success class 根本没有切上

而不是：

- 单纯由 `线条 / 粒子云 / 电平` 下拉项引起

这条的接手建议是：

- 后续继续追荧光粉问题时，优先看：
  - `src/hooks/useAudioRecording.js`
  - `src/App.jsx`
  - `src/index.css`
- 不要先把精力浪费在 `recordingAnimationStyle` 下拉项本身

1. 升版本
2. 本地验收
3. 再提交 / 推 tag

3. `electron-builder --mac --arm64 --publish never`
